Install, list, import

Any package manager works: pragma reads package.json and node_modules/. A client import must be in dependencies. Check the platform first: Intl, fetch, crypto.randomUUID() and structuredClone cost nothing.

npm i valibot dayjs --ignore-scripts
grep -A6 dependencies package.json
  "dependencies": {
    "dayjs": "^1.11.23",
    "es-toolkit": "^1.53.2",
    "highlight.js": "^11.12.0",
    "valibot": "^1.5.0"
  }

Each package becomes one file, /assets/npm/<package>-<hash>.js, with a modulepreload on the pages that import it.

Named imports: only what you use ships

Import only the names you need. These four names ship 0.94 kB gzip of valibot, not the whole package.

Load a package on click with import()

When a package is needed only after a click, import it in a utils/ module, then await import() that module in the action. The package does not load with the page, and the module keeps its import open to tree shaking.

What common packages cost

Gzip size of the /assets/npm/ file for each import, from pragma build on the test app in core/cli/xtask/packages/app. For scale: the starter page ships 12.3 kB gzip of JS, runtime included. CommonJS (dayjs, lodash) ships whole.

Tree shaking, measured: highlight.js

The code on this site is colored by highlight.js. The package index pulls in all 193 languages; highlight.js/lib/core plus three grammars is 95% smaller. It runs in load on the server; the browser loads it only on the SEO page, with import().

Packages that fail the check

Real pragma check output. The error points at the import. UI frameworks are rejected because the runtime owns the DOM. Node built-ins run only in .server.js. TypeScript, JSX, .vue, .svelte and packages that import CSS fail with app/package.

cat routes/shop.js
import { useState } from 'react'
import { groupByy } from 'es-toolkit'
import { readFile } from 'node:fs/promises'
import { nanoid } from 'nanoid'
import { format } from 'https://esm.sh/date-fns'
pragma check
shop.js:1 [js/import] package "react" is a UI framework; in pragma markup lives in .html and the runtime owns the DOM
shop.js:2 [js/import] `groupByy` is not exported by es-toolkit
shop.js:3 [app/package] `node:fs/promises` is a Node module and doesn't run in the browser; use it in a .server.js
shop.js:4 [js/import] package "nanoid" is not in package.json dependencies; install with `npm i nanoid` or `bun add nanoid`

Packages on the server

A .server.js file can import any package from package.json and Node built-ins (node:fs, node:crypto) without listing them. Server code is not bundled: Node resolves node_modules at run time.

WebAssembly on the server

A .server.js file can import a .wasm file. The import gives a compiled WebAssembly.Module on Node and on Workers. Here routes/_add.wasm exports one function, add.

pragma build copies the file to dist/server/ and adds the CompiledWasm rule to dist/server/wrangler.jsonc. Workers cannot compile WebAssembly from bytes, so give a package the imported module (Emscripten packages: instantiateWasm).

Workers modules and client imports

cloudflare:workers, cloudflare:sockets and the other cloudflare:* modules work in .server.js on Workers only. On Node (pragma dev, pragma serve) env from cloudflare:workers is the same env that load gets; any other export throws when it is used. Prefer the env that load and actions get. In the browser, both imports fail the check:

cat routes/stats.html
<script>
  import addWasm from './_add.wasm'
  import { env } from 'cloudflare:workers'
</script>
