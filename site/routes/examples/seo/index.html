Layout defaults, page overrides

A tag at the top level of a page replaces the layout tag with the same name, property, http-equiv or rel + hreflang, in place; a tag the layout lacks, like canonical, is appended. <html lang> comes from lang in pragma.json, and charset and viewport are always emitted.

Keep canonical and og:url out of the layout, or every page claims the same address. X reads og:title, og:description and og:image when the twitter:* versions are missing, so this site's layout sets only twitter:card, and a page overrides og:* once for both. Add a twitter:* tag only when X should show something else, like the shorter title on this demo page.

Tags from server data with ssr = true

Write {data.post.title} inside <title>, and :content, :href or {} in an attribute of <meta> and <link>, reading data, params or query; then add export const ssr = true to the route's .server.js. The server fills them before it sends the page, so a link-preview bot, which never runs JavaScript, sees the article instead of the site defaults.

Build absolute URLs in load from a fixed origin, never from the request's Host header. A missing value keeps the static fallback, such as the <title> text; a <meta> left without content or a <link> without href is dropped. On client navigation the router replaces <title>, <meta> and <link> with the next page's.

Soft 404 and real 404

load returns data, not a status, so a dynamic route whose entity is missing still answers 200: a soft 404, which search engines may index as an empty page. Bind <meta name="robots"> to data.head.robots and return 'noindex' only for the missing entity; in every other case the value is undefined and the tag is dropped.

An address that matches no route gets routes/_404.html with status 404, from pragma serve, the Node adapter and Workers alike.

robots.txt and a sitemap

Files in public/ are served from the site root as they are, with the right content-type. Routes only produce HTML, so sitemap.xml is a static file too: write it by hand, or generate it from your data with a script before pragma build, and point to it from robots.txt with a Sitemap: line.

Structured data with JSON-LD

Write one <script type="application/ld+json"> per schema at the top level of the page. The build moves it into <head> and rejects invalid JSON with the line and column. Inside its strings, {data.article.title} works as it does in a <meta>: with ssr = true the server writes each value JSON-escaped, so a quote in a title cannot break the script. JSON-LD without {} is static and needs no ssr.

The field notes article in the showcase above declares an Article from the same data as its title and Open Graph tags. This is what the server sends:

curl -s http://127.0.0.1:5181/examples/seo/demo/head-tags-from-data | grep -A11 ld+json
<script type="application/ld+json">
{
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": "Head tags rendered from server data",
  "description": "With ssr = true, bound title, meta and link tags are filled on the server, so previews show the real entity.",
  "image": "https://pragma.dev/og.png",
  "datePublished": "2026-11-16",
  "mainEntityOfPage": "https://pragma.dev/examples/seo/demo/head-tags-from-data",

</script>
