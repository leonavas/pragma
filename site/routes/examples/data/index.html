load() with a skeleton

load() runs on the server, and its return value is data: {data.loadedAt} in HTML, data.products in a script. Switch categories to watch the skeleton.

load receives { params, query, request, env, log }. The build adds a script to <head> that starts GET /_data/<path>?<query> before any module loads, and the page shows the <if page.loading> branch until it resolves. Every navigation, including a query change, runs load again. The page's own <script> only derives which category link is current from query.

The prebuilt HTML carries the loading chain as an inert template: the skeleton appears once the boot script runs, while content outside the chain, like the category links, is visible immediately. request is the Fetch Request (headers, cookies); env holds the Workers bindings, and on Node it is process.env. Using data.* on a page without a load fails check.

Helpers whose name starts with _ and ends in .server.js are private to the folder and never reach the browser; JSON is imported with with { type: 'json' }. A client module that imports a .server.js file fails pragma check with js/import, and node:* imports are allowed only in server files.

A form backed by a server action

Writes go through call('sign', input), imported from 'pragma', which runs actions.sign in the page's .server.js.

@submit calls preventDefault() for you, then sign() sends a POST /_action/<current path>/sign with a JSON body. data is live: assigning data.guestbook re-renders the list. A non-2xx response makes call throw with the server message, which the component keeps in its let error.

call works from a component too and always targets the current page's .server.js: this guestbook calls routes/examples/data/index.server.js. A server action may return a raw Response to pick the status, here a 422 for invalid input. Actions also receive query and request.

The endpoint answers 404 for an unknown action, 400 for a body that is not JSON and 405 for anything but POST. Actions are the only write path: there are no /api routes and no GET endpoints, so nothing can serve RSS, a sitemap or raw JSON dynamically.

ssr = true: data in the first HTML

With export const ssr = true in the .server.js, the server renders the page with its data, so the skeleton never appears. Reload the frame and the counts arrive already in the HTML.

The line must be literally export const ssr = true. The server runs load, renders the page into <main data-page>, every {data.x} included, and appends the data as <script type="application/json" id="pragma-data">. The client binds to that HTML without re-rendering and without a second fetch. The response is text/html with cache-control: private, no-cache, HEAD works, and a client-side navigation to an SSR route fetches the rendered HTML from the server instead of the prebuilt file.

Only data, params, query, page and <for> variables render on the server. $hydratedAt is script state, so it is empty in the HTML and gets the time when mount() runs. Head tags take {} too, but only with SSR: this route writes <title>{data.votes} votes · SSR demo</title> and the same in og:title, so link previews see the live count (SEO and head).

When load throws

An error thrown in load reaches the page as page.error.

The response is HTTP 500 with {"error":{"message"}}, an ERROR log on the server, and {page.error.message} on the client, rendered by the <else-if page.error> branch. Content outside the loading chain, like the filter links, keeps working. "Not found" is not an error: return { product: null } and render it.
