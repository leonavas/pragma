A counter with props and per-instance state

Props are attributes on the tag; state lives in the component's .js, one copy per instance.

Static props like start="10" are build-time literals, read as $start in HTML and ctx.$.start in JS. In JS they arrive as strings, except a bare attribute or "true" (true) and "false" (false), so the counter converts with Number(). state(ctx) runs once per instance; derived values such as atMinimum are getters, recomputed on every render.

The component lives in _components/counter/ next to this page, so it is used as <p-counter>. Moving the folder to lib/components/ would make it <c-counter> for every route.

Slots: content that belongs to the caller

A component places the caller's children with <slot>; those children keep their own owner.

npm packages are bundled with rolldown and tree-shaken per route.

<slot> receives the children and <slot name="actions"> receives the children marked slot="actions". Children of a <slot> are fallback content, rendered only when the caller passes nothing: the second panel shows it.

The Like button sits inside <p-panel>, yet @click="like" and $likesText resolve in the page module, while Hide calls the panel's own toggle, with separate state per instance.

In a component without .js, $plugin.name is an alias to the caller's path at any depth, and :model="$value" writes straight back into the page's $query, so the search field needs no code at all.

In a component with .js, $plugin still works in HTML, but ctx.$.plugin is the attribute string ("[object Object]"). Objects only travel in HTML: to use one in JS, pass an id or scalar (:id="plugin.id") and look it up in ctx.data or a store. A component with .js also cannot receive the caller's $x; pass data., shared. or a <for> item.

Bare boolean props, class and slot fallback

A component without .js is fully expanded at build and ships zero JavaScript.

caller text

A bare attribute like active is truthy; "false" and "" are falsy. class on the tag is appended to the root's classes; id is an ordinary prop that you apply with :id="$id".

The same prop, read from HTML and from JS

A prop has the same truthiness in HTML and in JS.

A missing prop, "" and "false" are falsy; a bare attribute and any other value are truthy. In JS a bare attribute or "true" arrives as true and "false" as false; every other prop is a string, so convert numbers yourself (Number(ctx.$.step)).

In a component with .js, $x is state when x is a key of the object state() returns, and a prop otherwise. Write state as () => ({ … }) with plain keys and no spread, so the build can tell the two apart. Do not name a state key or getter after a prop: the key hides the prop, and a getter that reads ctx.$.<same name> recurses forever.

Where a component lives decides its tag

Every component on this page sits in routes/examples/components/_components/, so it is a <p-…> visible to this folder and the folders below it. The lookup walks up from the page folder to routes/, so routes/_components/x/ is visible to every route. lib/components/x/ makes it <c-x> everywhere; promoting one is a move plus a rename from p- to c-.

  • p- names are private to their folder, styles included. This page and the syntax page each have their own <p-badge>; the build gives each one its own data-c, so both write [data-c="badge"] in their .css and never share a rule.
  • A <p-x> used outside routes/ is an error, and so are two components with the same folder name on one page (<c-card> plus <p-card>).
  • A component cannot have a .server.js: its data comes from the page's load, as in the list above.
  • A component cannot use itself, and its root cannot be <template>, <slot> or another component.
  • A component's .js loads only on pages that use it. Its .css goes into the single app stylesheet, scoped by its data-c.
