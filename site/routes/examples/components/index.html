One file: script, markup and style

A top-level let is state, export let is a prop, a function is an action or a derived value, and {$count} puts a value in the text.

  • export let start = 0 declares a prop with a default. The default's type converts the attribute: start="10" arrives as the number 10, so no Number() anywhere. Props are read-only: let count = start copies one into state.
  • const atMinimum = () => … is a derived value: used in a binding (:disabled="$atMinimum"), it runs on every render. In JS you call it: atMinimum().
  • function increase(event) is an action when an event names it. Without parentheses, @click="increase" passes the DOM event, here to read event.shiftKey. Assigning count schedules one render per microtask; there is no setState and no this.
  • With parentheses the function gets only what you list: paths, literals, event and el, the element that has the @. Reset hides itself after a click, so @click="reset(el)" moves the focus to + and keyboard users keep their place.
  • A store function works the same way, with no wrapper: @click="shared.cart.add(product)". A component that only reads and calls a store needs no script, as on the stores page.
  • <style> is scoped by the build: .counter-step only matches the markup this component wrote, with no added specificity, so write plain selectors. :global(…) opts out only what is inside it (:global(html[data-theme="dark"]) .counter-step is still this component's buttons), and the root itself is [data-c="counter"]. A separate counter.css works the same way; having both it and the <style> (or a <script> and a counter.js) is a check error (html/duplicate-module).

The component lives in _components/counter/ next to this page, so it is used as <p-counter>. Moving the folder to lib/components/ would make it <c-counter> for every route.

No script: build-time props, class and slot fallback

A component without a script is fully expanded at build and ships zero JavaScript.

caller text

Without a script, {$label} is replaced by the caller's text at build time. A bare attribute like active is truthy; a missing one, "" and "false" are falsy. class on the tag is appended to the root's classes.

Typed props: the default decides the type

An attribute is always text; export let converts it with the type of its default.
  • A number default turns "5" into 5. A boolean default turns a bare attribute or "true" into true and "false" into false. A string default keeps the text. Any other default (an object, null) takes the value as passed with :prop="path".
  • A missing attribute gives the default. HTML (<if $locked>) and JS (locked) read the same converted value.
  • An attribute the script does not declare is an error at the call site (html/unknown-prop), and assigning a prop is js/prop-write.

Where a component lives decides its tag

Every component on this page sits in routes/examples/components/_components/, so it is a <p-…> visible to this folder and the folders below it. The lookup walks up from the page folder to routes/, so routes/_components/x/ is visible to every route. lib/components/x/ makes it <c-x> everywhere; promoting one is a move plus a rename from p- to c-.

  • p- names are private to their folder, styles included. This page and the syntax page each have their own <p-badge>; the build gives each one its own data-c and scopes each <style> to it, so both write .badge-icon and never share a rule.
  • A <p-x> used outside routes/ is an error, and so are two components with the same folder name on one page (<c-card> plus <p-card>).
  • A component cannot have a .server.js: its data comes from the page's load, as in the list above.
  • A component cannot use itself, and its root cannot be <template>, <slot> or another component.
  • A component's script loads only on pages that use it. Its <style> goes into the CSS of the routes that use it, scoped to the markup it wrote.
