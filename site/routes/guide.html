    Install

    pragma is one Rust binary. It compiles, checks, serves and bundles npm packages by itself: no Vite, no esbuild, no config. You need a Rust toolchain (cargo, from rustup) to build it. Node 22 or newer is needed only when an app has .server.js files, because pragma dev, pragma serve and the Node adapter run them.

    git clone https://github.com/leonavas/pragma
cd pragma
cargo install --path core/cli/crates/pragma-cli
     
    pragma -V
pragma 0.1.0
pragma --help
pragma — HTML, CSS and JS without a framework

usage:
  pragma new <dir>                              create an app in <dir> (empty or missing)
  pragma dev [--port 5180] [--host 127.0.0.1]   dev server with live reload
  pragma build                                  build dist/ for production
  pragma check [--strict]                       check HTML, CSS and JS (--strict: warnings become errors)
  pragma serve [--port 3000] [--host 127.0.0.1] serve dist/ as in production
  pragma upgrade                                update .pragma/ (runtime, docs, base.css, version) to this version
  pragma self-update [version]                  update the pragma CLI binary from GitHub Releases

options:
  -h, --help      show this help
  -V, --version   show the version

    Options take either form, --port 8080 or --port=8080. The cargo install output and the clone progress are left out above.

    To update, run git pull and the same cargo install, then pragma upgrade inside each app. It makes the app's .pragma/ (runtime, docs, base.css) match the new binary, prints every file it updated, added or removed, and never touches anything outside .pragma/. Until then pragma check warns with app/core-outdated.

    Create an app

    pragma new writes a working app into an empty or missing folder: a layout, a home page with a modal, an alert and a dropdown, a 404 page, the theme, the runtime in .pragma/ and the docs in .pragma/docs/.

    pragma new my-app
app created in my-app (41 files)

  cd my-app
  pragma dev

    The app ships an AGENTS.md (and a CLAUDE.md that includes it) with the syntax in a dozen lines, the rules the compiler enforces and a table that maps each task to one file in .pragma/docs/. A coding agent reads that first; you can too. The docs are short on purpose: every page fits in a context window.

    Your first component

    A component is a folder with one .html file: an optional <script>, the markup, an optional <style>. In the script, a top-level let is state, a function is an action when an event calls it and a derived value when the markup reads it, and export let declares a prop. In the markup, {$count} puts a value in the text, @click calls a function and :disabled binds an attribute. Assigning a variable is all it takes to update the page.

    Use it on any page. The build expands it in place, so its markup is in the prebuilt HTML, and its script loads only on pages that use it: a page with just this counter loads 8.9 kB of JS, runtime included.

    <c-counter label="Cups of coffee" start="1"></c-counter>
    • The default sets the prop's type: start="1" arrives as the number 1 because the default is 0; a bare attribute is true.
    • Props are read-only and live. let count = start copies one into state that the component can change.
    • The <style> is scoped to the markup the component wrote; utilities from classes.md cover the rest.
    • pragma check reads the script: a name the markup uses but the script lacks is html/unknown-name, an attribute the component does not declare is html/unknown-prop, a write to a prop is js/prop-write.

    Project structure

    The layout is fixed, so there is nothing to configure and only one place for each thing. The files below are exactly what pragma new creates, minus .pragma/.

    pragma.json               name, lang and webmcp
AGENTS.md  CLAUDE.md      rules for coding agents
routes/
  _layout.html            header, footer, site-wide <head>; <slot> is the page
  _404.html               unknown URLs
  index.html              /         (markup, its <script> and <style>)
lib/
  components/<name>/      <c-name> for every page: modal, alert, dropdown
  state/<name>.js         stores, reached as shared.<name>
  theme.css               tokens and the few custom classes
utils/                    plain JS modules
public/                   copied as is: favicon.svg, images, fonts
.pragma/                  runtime and docs; never edited
    • Only routes/, lib/, utils/, .pragma/ and public/ are read. Other top-level files, like a README, are ignored.
    • A page is routes/x.html, with an optional <script> and <style> at its top level and an optional x.server.js (load, server actions, ssr). A large script can live in x.js beside it instead, never both (html/duplicate-module).
    • Anything else in routes/ must be private, with a leading underscore: _components/, _products.json, _catalog.server.js.
    • pragma.json takes exactly name (required: fallback title, log service name, Worker name), lang (default en) and webmcp (default true). Unknown keys are errors.

    Develop

    pragma dev builds into .pragma/dev/, watches the folder and reloads every open tab on each save, over one WebSocket per tab. CSS changes swap in place without a reload. When a save breaks the build, the terminal prints the problem and the browser shows it in a full-screen overlay; pages without errors keep working, and the next good save clears it.

    When the app has a .server.js, dev starts Node next to it, proxies /_data, /_action and /_otel, and restarts it when server code changes. Server logs, debug included, and every log record sent by the browser print in the same terminal.

    The rules form a closed list. Anything outside the syntax is an error with a pointer to the fix, so an agent cannot quietly drift into another framework's habits.

    • JS: js/syntax, js/comment, js/console, js/vague-name, js/html-in-js (no innerHTML or createElement), js/jsdoc-types, js/import, and the script rules: js/component-script (no var, no top-level await, export only for props), js/prop-write, js/const-state (a mutated const the markup reads), js/store-import (stores only through shared) and js/legacy-api (the old state(ctx) API, with the migration).
    • HTML: html/syntax (close every non-void tag), html/comment, html/script, html/duplicate-module (a <script> and an x.js for the same file), html/style-inline, html/on-inline, html/legacy-syntax, html/unknown-directive, html/invalid-path, html/invalid-root, the block rules (html/block, html/for-without-key, html/misplaced-else…), html/unknown-name, html/unknown-prop, html/component, html/unknown-component, html/layout, html/title, html/class (no :class), html/text-removed (no :text), html/interpolation (no {{ }} or ${ } outside <code>/<pre>), html/data-attribute (no hand-written data-*) and html/head (<meta> and <link> only at the top of a page or in the layout head). html/unknown-directive also names the pragma form for Vue, Alpine, Svelte, Angular and React attributes.
    • CSS: css/syntax, css/comment, css/unknown-class (only the utilities in classes.md and classes your CSS defines), css/arbitrary-value.
    • App: app/structure, app/route-conflict, app/package, app/pragma-json, and the warning app/core-outdated when .pragma/ differs from the installed binary.
    • Accessibility, checked on the expanded page with components inlined: img-alt, accessible-name, label, dialog-name, click-non-interactive, heading, single-h1, tabindex, duplicate-id, iframe-title, a-no-href. A bound attribute counts: :aria-label satisfies aria-label.

    Performance

    pragma build prints the JS each page loads, gzip, runtime included, and the CSS size. The numbers are information only: no limit fails the build.

    pragma build
page     JS gzip
/        12.5 KB
CSS       3.9 KB
1 page(s)

    A page with no script of its own costs 8.7 kB gzip, all of it runtime. When a page grows, make the code smaller. What the build does to keep pages small:

    • Every route is prebuilt HTML, and a page with a load starts its data fetch from an inline script in <head>, before any module runs.
    • Exactly the modules a page imports get a modulepreload. Modules are minified and hashed one by one; there is no app bundle.
    • The CSS contains only the classes the app uses.
    • Links prefetch on hover, focus or when visible; navigations use view transitions.
    • HTML is served no-cache, /assets/ as immutable, both brotli or gzip compressed.
    • Code needed only after a click goes behind await import() in the action: not preloaded, not in the page size. See lazy packages.

    Serve and deploy

    pragma serve is a local preview of production: it serves dist/ with precompressed brotli and gzip, ETags and the production cache headers, and starts dist/server/node.mjs when there is one.

    Then pick a target. All three ship the same dist/client/.

    • Static hosting, for apps without .server.js: upload dist/client/. The host must serve /about from about.html, a param route such as /blog/x from blog/[slug].html, and unknown paths from _404.html with status 404. Generic static hosts usually cannot do param routes, and without a /_otel endpoint the client stops sending logs after the first 404 or 405.
    • Node: copy dist/ and node_modules, then run the adapter. It serves the files with the right types and cache headers, resolves param routes through the manifest, renders SSR pages and the 404 page, and answers /_data, /_action and /_otel. Node finds node_modules by walking up from dist/server/.
    • Cloudflare Workers: the generated wrangler.jsonc points main at worker.js and the assets binding at ../client; wrangler bundles the server code on deploy. Workers have no filesystem, and node:* imports in .server.js need "compatibility_flags": ["nodejs_compat"] added to that file.
    PORT=8080 node dist/server/node.mjs

    Under the hood

    Nothing here needs configuring, but it helps when you read the built HTML or debug a deploy.

    • The generated <head> comes in this order: charset, viewport, <title>, the layout's head tags (a page's own <meta> and <link> replace the layout's tag with the same name), the theme script when used, the stylesheet, the inline /_data fetch when the page has a load, the modulepreloads, the route JSON and the boot module.
    • The route JSON, a <script> with id="pragma-route", tells the runtime what to start: 
      {"pattern":"/orders","page":null,"components":{},"stores":{},"loader":true,"ssr":false}
    • /_pragma/manifest.json lists every route with its HTML file, modules, loader and SSR flag. The client router and the Node adapter both read it.
    • Data travels as GET /_data/<path> and server actions as POST /_action/<path>/<name>, both with a traceparent header.
    • Not in v0: static generation with data, catch-all routes ([...rest]), per-route CSS, i18n and Speculation Rules.
